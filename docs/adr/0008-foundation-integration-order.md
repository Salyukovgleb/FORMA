# ADR-0008: Порядок интеграции Compose и runtime

Владелец: backend architect. Статус: approved. Обновлено: 2026-10-31.
Связи: BE-009/011/012/013/032/051, ADR-0001.

## Контекст

Исходная BE-009 требует стартующих API/worker до реализации app factory BE-012
и worker BE-032. При этом BE-011 зависит от BE-009. Проверка всего runtime в BE-009
невозможна без нарушения зависимости либо фиктивных sleep-процессов.

## Варианты

1. Перенести весь Compose после worker: невозможно проверить DB bootstrap до Alembic.
2. Добавить фиктивные процессы: создаёт ложное доказательство готовности.
3. Выполнять инфраструктурную и runtime интеграцию поэтапно.

## Решение

BE-009 отвечает за воспроизводимую сборку non-root Python image, PostgreSQL Compose,
постоянные DB/files volumes и реальные тесты их сохранности при recreate.
API и worker не считаются реализованными в этой задаче. BE-011 использует PostgreSQL
из этого bootstrap. BE-012 добавляет API entrypoint/health и его Compose service smoke.
BE-032 добавляет worker entrypoint/heartbeat и его Compose service smoke.
BE-013 проверяет существующие API/DB images; worker smoke добавляется в BE-032.
BE-051 подтверждает совместный clean-room запуск всего runtime.

Топология зависимостей сохраняется; изменяется распределение acceptance checks между
уже существующими задачами. Новых сервисов и технологий не добавляется.

## Последствия

В README и STATUS чётко разделять инфраструктурный bootstrap и готовность API/worker.
BE-009 нельзя закрыть без реальных container/volume tests. Недоступность Docker остаётся
блокером локальной проверки. Фиктивные jobs и пропущенные проверки не считаются passed.

## Пересмотр

Пересмотреть, если меняется runtime упаковка либо появляется отдельная команда инфраструктуры.
